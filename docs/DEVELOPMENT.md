## 작업 순서

1. 실제 파일을 먼저 읽으세요. 사용자가 직접 수정하는 프로젝트입니다.
2. 변경 데이터가 프로젝트 저장·재열기와 JSON 내보내기 양쪽에 어떤 영향을 주는지 확인하세요.
3. 상태 변경은 commit과 연결하세요. UI 초안과 저장된 데이터를 구분하세요.
4. 오류는 notifyError로 알립니다. 자체적인 alert 창이나 인라인 오류 체계를 새로 늘리지 마세요.
5. 의미 있는 데이터 변경에는 회귀 사례를 추가하고 `npm test`, `npm run build`를 실행하세요.
6. 브라우저 검증을 하지 않았다면 완료 보고에서 그렇게 명시하세요.

현재 테스트는 Node 내장 test와 assert를 사용합니다. Vitest/Playwright는 설치되어 있지 않습니다. TypeScript 테스트는 Node의 타입 제거 기능으로 실행됩니다. 테스트에서 런타임 import할 TS 파일은 `.ts` 확장자를 확인하세요.

## UI 수동 검증 목록

- 큰 JSON에서 좌우 독립 스크롤과 툴바 고정, 사이드바 폭 일치.
- 일반/Ctrl/Shift 클릭, Ctrl 방향키 왕복 후 단일 선택.
- 1,000개 페이지 경계를 넘는 방향키·PageUp/Down·Home/End.
- 입력창·한글 조합·팝업 내부에서 전역 단축키 충돌 여부.
- 검색 토글, 결과 선택 후 원래 페이지 중앙 이동, 처음/끝 메시지.
- 캐릭터 변경/삭제/시스템 전환, 사용자 지정 해제, 표정 URL 수정.
- 채팅 전송 위치, Shift+Enter와 한글 Enter, 기본/선택 표정.
- 프로젝트 저장·재열기, 네 형식 다운로드, HTML의 외부 이미지.
- 팝업 위 오류 토스트, 닫기 버튼, 자동 사라짐.

## 알려진 한계 및 다음 담당자가 볼 점

- 자동 저장·복구가 없습니다. 편집 중 새로고침/닫기 보호도 포괄적이지 않습니다.
- 메시지 초안과 캐릭터 초안은 개별 컴포넌트 상태입니다. 탭 전환 등에서 미저장 초안 보존 정책을 통일할 필요가 있습니다.
- App.tsx에 상태와 핸들러가 집중되어 있습니다. 기능 변경과 대규모 리팩터링은 구분해 검토하세요.
- 페이지는 1,000개 DOM 렌더링이며 가상화가 아닙니다. 대용량 브라우저 성능은 측정하지 않았습니다.
- 병합 결과는 첫 sourceIndex만 유지합니다. 원본 전체는 보존되지만 합쳐진 각 메시지의 provenance 목록은 없습니다.
- 검색 위치 중앙 정렬은 스크롤 영역의 위아래 padding을 직접 조절합니다. 일반 키보드 이동에서 복원합니다. 향후 레이아웃 변경 시 확인하세요.
- 기존 시스템 이름과 동일한 이름의 일반 캐릭터, 손상된 프로젝트 선택 필드 등은 추가 검증 대상입니다.
- 브라우저 자동 통합 테스트가 없으므로 기존 단위 테스트 통과를 UI 검증으로 표현하지 마세요.
